# Karpathy Guidelines

源自 Andrej Karpathy 关于 LLM 编码陷阱的观察总结的行为指南。

**权衡：** 这些指南偏向谨慎而非速度。对于简单任务，可自行判断。

## 1. 编码前先思考

**不假设、不隐藏困惑、呈现权衡。**

在实现之前：
- 明确陈述你的假设。如果不确定，要问。
- 如果存在多种理解，呈现它们——不要默默选择。
- 如果存在更简单的方法，指出它。在合理时提出反对意见。
- 如果有不清楚的地方，停下来。说出什么让你困惑然后问。

## 2. 优先简洁

**解决问题所需的最少代码。不做推测。**

- 不添加需求之外的功能。
- 不为单次使用的代码创建抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不处理不可能出现的错误场景。
- 如果你能用 50 行解决就不要写 200 行。

问自己："一个资深工程师会说这过度复杂吗？"如果是的，简化。

## 3. 精确修改

**只触碰必须触碰的。只清理自己的烂摊子。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有风格，即使你用不同方式来做。
- 如果注意到无关的死代码，提及它——不要删除。

当你的更改造成孤儿时：
- 删除因你的更改而变得未使用的 import/变量/函数。
- 不要删除预先存在的死代码，除非被要求。

检验标准：每一行更改都应该能追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写能复现它的测试，然后让通过"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，简要陈述计划：
```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
3. [步骤] → 验证: [检查项]
```

强有力的成功标准让你能独立循环。弱标准（"让它工作"）需要不断的澄清。

## 与现有 Superpowers 的协同

此 skill 与项目中的其他 skill 互补：

| 搭配 Skill | 协同效果 |
|------------|----------|
| `brainstorming` | "编码前先思考"的具体流程：探索、提问、设计 |
| `test-driven-development` | "目标驱动执行"的具体实现 |
| `systematic-debugging` | "精确修改"的调试流程 |
| `verification-before-completion` | "循环验证"的完成检查 |

## 触发时机

在以下情况下使用此 skill：
- 编写新代码时
- 审查代码时
- 重构现有代码时
- 遇到任何"这应该怎么做"的问题时
